# 资产充值 dev 联调协议草案

供资产服务方与社区侧逐项确认。以下路径、字段、状态和错误码均为提案。当前站内充值入口保持关闭。资产任务报价及本机项目预算沿用各自的流程。

## 订单与回执

| 操作（提议） | 请求与响应约定 |
| --- | --- |
| `POST /v1/topups` | 传 `offer_id` 和 `Idempotency-Key`。服务端从已验证凭据取得账号和环境，从当前报价锁定支付金额、币种、入账数量和单位。返回 `order_id`、锁定报价、`status`、`expires_at` 和服务方托管的 `checkout_url`。报价过期或已变更时要求用户重新确认。 |
| `GET /v1/topups/{order_id}` | 按凭据绑定的环境和账号查询，越权和不存在均返回 404。响应含创建、更新时间、支付和退款状态、到账回执及冲正回执。结果页凭 `order_id` 重新查询。回跳参数只用于定位订单。 |
| `POST /v1/topups/{order_id}/cancel` | 仅待支付订单可撤销，带幂等键。遇支付与撤销竞争由服务方核对最终支付结果，返回最新订单，已扣款须对账或退款。 |
| `POST /v1/topups/{order_id}/refunds` | 仅有退款权限的服务角色可发起，带独立幂等键并关联原回执。建议首版只支持全额退款。服务方须明确是否支持、可退期限、积分已消费时的规则，社区按已确认能力展示。 |

`payment.amount` 与 `payment.currency` 表示用户实际支付的十进制主币单位及币种。`credit.amount` 与 `credit.unit` 表示锁定的到账数量和账本单位，两者均用十进制字符串。服务端报价须给出二者的对应值与允许精度。界面按回执显示，避免从支付金额推算到账数量。

## 状态与幂等

- 创建后为 `pending`。支付渠道确认后为 `paid`，持久化到账流水后为 `credited`。`paid` 时结果页显示「已支付，等待到账」。未支付订单可进入 `cancelled`、`expired` 或 `failed`，不生成到账流水。
- 退款以独立记录返回 `pending`、`succeeded` 或 `failed`。成功后生成关联原流水的冲正回执，保留原始入账。退款失败保留原账务状态。每张回执含唯一流水号、原订单、环境、账号、发生时间、方向、数量和单位。
- 创建、撤销和退款按环境、账号、操作及幂等键去重。相同请求重试返回原结果，同键异参返回 409。请求超时后沿用原键重试，支付成功后只轮询订单。
- 支付服务处理回调时校验原始报文签名、签名时间窗和事件 ID，再核对渠道订单、环境、金额与币种。先校验事件符合订单状态，再在同一事务中去重事件、按订单唯一业务键写流水并更新状态。重复或乱序回调、不同事件 ID 指向同一笔支付均不能重复入账。回调与对账补偿共用该约束。退款按退款单唯一键处理。

## 沙箱交付与验收

服务方需交付接口版本与实际路径、沙箱 base URL、鉴权方式、报价与精度、状态和错误码映射、支付渠道的签名规范与密钥轮换方式、回调重试策略、沙箱账号 A/B 和事件模拟方式。凭据经私有渠道交付。社区凭这些材料接订单及结果页，双方保留脱敏订单号、流水号与查询响应作为证据。

| 沙箱用例 | 预期账务结果 |
| --- | --- |
| 创建请求响应丢失，原键重试；同键改报价 | 一个订单；异参冲突 |
| 支付成功，回跳早于回调；随后重复通知和对账 | 页面先显示处理中；最终一笔到账，回执单位和数量等于锁定报价 |
| 支付失败、过期、撤销；超时后又收到支付成功 | 未扣款订单零入账；实扣与本地终态冲突进入对账并给出可查询处理结果 |
| 错签、过期签名、金额或币种不符 | 拒绝更新订单和账本 |
| B 查询或撤销 A 的订单；跨 dev/正式环境查询 | 拒绝访问，订单和账本均不变 |
| 全额退款、重复通知、模拟退款失败 | 成功只冲正一次；失败保留原入账及失败记录 |
